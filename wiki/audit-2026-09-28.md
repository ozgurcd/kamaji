# Kamaji working-tree audit

Historical initial audit: the findings, line numbers, dependency transitions,
and failing checks below describe that audit's tree. They are preserved as
evidence. Subsequent core fixes, YAML consolidation, instance refactoring, and
passing validation are summarized in [the repository page](repos/kamaji.md),
[general-review follow-up](../docs/GENERAL_REVIEW.md), and
[testing record](../docs/TESTING.md). Extension findings remain deferred.

Reviewed on 2026-09-28 at HEAD `84aadbd23ef831c332107363934a03c6d335d1c5`, including
the owner's existing uncommitted Go changes and untracked commands/utilities/rules.
Product bugs below were inspected, not repaired. Dependency upgrades are separate.

## Scope and interpretation

Reviewed every function in the gograph inventory of 14 repository Go files
(11 production files plus three test files), all six Python source files under
`rules/`, README, usage documentation, dependency declarations, the root BUILD
file, rule schema, and tracked-file inventory. Generated binaries, virtual
environments, credential files and real infrastructure state were not audited.
No real Terraform, Kubernetes, 1Password, or credential operation was performed.

P1 means serious security exposure, lost functionality, or risk of operating on
the wrong target. P2 means a concrete crash, incorrect result, portability or
reliability problem. P3 means repository hygiene. “Reproduced” means an actual
repository function was exercised with confined synthetic inputs; “static” means
the finding follows from inspected source, with its trigger stated below.

The CLI currently rejects ordinary target names (F01), so runner, downloader,
and extraction findings describe callable package behavior and defects that
become CLI-reachable once target dispatch is restored. Python library findings
likewise require their functions to be invoked; two rule files lack entry points
(F31). This is a comprehensive review of this source inventory, not proof that
every possible defect has been found.

## Findings

### F01 — P1: Normal target execution is disconnected

`cmd/root.go:22-32`, `main.go:14-20`. Cobra registers only administrative commands;
`kamaji staging` is rejected as an unknown command. The root handler itself only
checks for missing arguments and never parses a build or calls the runner.
gograph reports no callers for `runner.Run`; the positive control finds callers
for `rt.InitRuntime`. Reproduced by calling `cmd.Execute` in a subprocess without
running `main` or reading user configuration.

### F02 — P2: CLI flags never reach the runtime

`cmd/root.go:15-19,35-39`, `main.go:22-55`. `--build`, `--debug`, `--cleanup`,
`--isolated` and `--python` bind private variables that are never copied to
`rt.Config`. The runtime therefore sees zero values and the Python flag loses
to environment/config/default resolution. Static, over the entire cmd package.

### F03 — P2: Initialization happens after command execution

`main.go:17-19`, `cmd/root.go:42-82`, `rt/python_env.go:12`. Administrative commands
run before configuration/runtime setup. `setup-python-env` therefore uses an
empty `TmpDir`, creating `venv` relative to the caller. After a successful
administrative command or `--help`, main still initializes a workspace and can
exit with “workspace file not found”; help can create cache directories when a
workspace exists. Static. Global installation commands were not executed.

### F04 — P1: Shell injection and argument corruption

`runner/runner.go:18-58,149-158`. Interpreter, rule path, scalar values and trailing
arguments are concatenated into `bash -c` text. Spaces split arguments;
metacharacters execute shell commands; single quotes inside serialized JSON also
break quoting. Reproduced with `/usr/bin/true` and a harmless `printf` marker
inside the audit directory. Pass an argument vector to `exec.Command` instead.

### F05 — P1: Empty workspace variables panic

`runner/runner.go:170`. Missing, null, or empty `workspace_vars` leads to an
unchecked `WorkspaceVars[0]`. Reproduced through `runner.Run` with synthetic
configuration; the panic occurs before launching a child process.

### F06 — P2: Malformed metadata panics

`execroot/execroot.go:17-19`. Empty/truncated metadata or any metadata without a
comma causes `parts[1]` to panic. Reproduced through
`CopyThirdPartyIntoExecRootDir`. File names containing commas are also parsed
incorrectly by the unescaped comma-separated representation.

### F07 — P1: Tar paths can escape the extraction directory

`execroot/execroot.go:114-126`. `header.Name` is joined to the destination without
confinement validation. A `../escaped` entry writes outside `__TMP__` before a
later chmod fails. Reproduced entirely inside the audit sandbox. More traversal
components can reach other writable paths. Archive hashes authenticate bytes,
not their safety. Existing symlinks are also followed by tar/ZIP output opens
(`tools/tools.go:189-210`); ZIP's lexical `Rel` check alone does not prevent that.

### F08 — P2: Tar extraction assumes a Darwin ARM64 layout

`execroot/execroot.go:67`. Every tarball must contain
`darwin-arm64/<binary>` for chmod, even on Linux or when the executable is at
archive root. Reproduced with a valid root-level `payload` archive.

### F09 — P2: Valid tar entries without preceding directories fail

`execroot/execroot.go:120-129`. Regular files do not create parent directories,
so a valid archive containing `nested/payload` without a separate `nested/`
entry fails. Reproduced. Tar symlinks/hardlinks are rejected outright rather
than supported or documented as unsupported.

### F10 — P2: Raw Linux executables are unsupported

`execroot/execroot.go:75-85`. Dispatch accepts ZIP, Mach-O and gzip but not ELF,
despite runtime supporting Linux. Reproduced using ELF MIME metadata; no binary
execution was attempted.

### F11 — P2: Dependency file paths are treated as basenames

`tools/tools.go:237-250`, `execroot/execroot.go:177-186`. `GetFullPath` compares
`info.Name()` with the entire configured name, so `bin/payload` never matches.
Duplicate basenames are ambiguous; a directory can match too. The external
symlink also lacks creation of nested destination parents. Reproduced relative
path failure with a successful basename control.

### F12 — P2: Failed downloads permanently poison the cache

`target/target.go:195-199,272-284,297-318`. Creating the cache directory is enough
to make future calls take the cached branch. Interrupted downloads, hash
mismatches or missing metadata are not evicted/rebuilt. A retry returns “file is
invalid” indefinitely or later fails to read metadata. Reproduced offline with
a partial cached file and an intentionally unusable URL.

### F13 — P2: Shared cache updates are not atomic

`target/target.go:267-295,332`, `execroot/execroot.go:22-73`. Concurrent invocations
share `<hash>/file`, `metadata` and `__TMP__` without locking or atomic rename.
One process can truncate a file while another validates/extracts/executes it.
Reusing one archive under different configured `file_path` values also reuses
the first metadata filename (`tools/tools.go:61`, `execroot/execroot.go:165-178`).
Static concurrency and cache-key analysis; not a stress-test result.

### F14 — P2: Downloads and extraction have no resource bounds

`target/target.go:321-338`, `execroot/execroot.go:100-132`,
`tools/tools.go:154-210`. The default HTTP client has no overall timeout;
downloads and archive expansion have no byte/entry limits. A stalled server can
hang indefinitely, while oversized or highly compressed content can exhaust
disk. Static; no live download attack was run.

### F15 — P2: Rule symlinking supports only a narrow path shape

`runner/runner.go:101-123`. A flat rule such as `rule.py` tries to symlink over
the already-created `rules` directory and fails with “file exists” (reproduced).
A multi-level rule such as `a/b/rule.py` lacks intermediate destination parents.
The documented `//` rule notation is not normalized before command construction;
the separate `GetRule` helper is not called and uses `WorkspaceRoot`, whereas
workspace detection sets `WorkspaceDir` (`tools/tools.go:28-31`,
`rt/runtime.go:79`). Static for nested and `//` variants.

### F16 — P2: Working-directory selection trusts stale PWD

`runner/runner.go:132-135,161-165`. Execution and isolation use the `PWD`
environment string instead of `os.Getwd`. A launcher that changes cwd without
updating PWD can run infrastructure commands in the wrong directory. Static.

### F17 — P2: Isolation writes through to original files

`tools/tools.go:264-311`, `runner/runner.go:130-139`. The isolated directory
symlinks original files and whole subdirectories. Overwriting an existing file
or modifying a linked subdirectory changes the source workspace. Reproduced
with a harmless text file. This is working-directory separation, not write
isolation, and contradicts the README's stronger controlled-environment claim.

### F18 — P2: Nested configuration structures are not serialized reliably

`tools/tools.go:140-152`, `runner/runner.go:19-47`. Maps inside slices are not
normalized, so JSON marshaling rejects `map[any]any` elements. String-keyed maps
and lists passed directly to the API instead fall through to Go `%v` formatting,
not JSON. Reproduced the surviving non-JSON map inside a list.

### F19 — P2: Rule validation ignores required/default declarations

`target/target.go:84-153`, `rules/run_terraform/rule_definition.yaml:3-19`.
Missing variables print a message and continue, including those marked
`mandatory: true`; defaults are never applied. Invalid schema entries can also
print and continue. This allows omitted values to reach Python as `None`.
Static; validator is currently disconnected along with target dispatch.

### F20 — P2: Error-returning helpers terminate the process

`runner/runner.go:177-179`, `target/target.go:190-193`,
`tools/tools.go:101-104`. Child failure, missing dependency configuration, and
an unreadable/empty artifact call `log.Fatalf` instead of returning their error.
Callers cannot recover; deferred cleanup is bypassed and child exit status is
collapsed to 1. Static. This is separate from intentional exits at CLI entry.

### F21 — P1: Debug logging exposes sensitive values

`runner/runner.go:153-154`, `rules/common/terraform.py:64,154-171`,
`rules/common/one_password.py:84`. Complete command/config values, child
environment values, backend configuration and parsed secret values are logged.
The exposure is conditional on logging/debug being enabled; OnePassword values
are logged as explicit name=value strings. Static only: no real secret was
loaded or used to demonstrate it.

### F22 — P2: The created Python environment is not selected for execution

`rt/python_env.go:12-15`, `main.go:26-30`, `runner/runner.go:63-72`.
Setup creates `<TmpDir>/venv`, but normal execution selects configured Python or
`python3`/`python`, never that venv automatically. Packages can be successfully
installed but missing from the interpreter that runs rules. Setup also ignores
the configured Python executable and requires an unrelated global-directory
write check in `cmd/root.go:73`. Static.

### F23 — P2: Terraform import happens before its path setup

`rules/run_terraform/run_terraform.py:11,59-62`, `runner/runner.go:157`.
With omitted `rules_common_directory`, Go sets PYTHONPATH to the rules root,
but Terraform is under `common`. The top-level import fails before Python adds
that common directory. Reproduced even with `--help` and a sanitized environment.

### F24 — P2: Optional logging argument crashes

`rules/run_terraform/run_terraform.py:15-16,35,46`. Omitted `--log_verbosity`
passes `None` to `.upper()`; the function's default parameter does not apply to
explicit None, and only ValueError is caught. Reproduced.

### F25 — P2: Required execution settings have broken error paths

`rules/run_terraform/run_terraform.py:39-55,64-66,116`,
`rules/common/terraform.py:105,117-119`. Omitted region/workspace are `None`,
not the empty string being checked; environment assignment/subprocess arguments
then fail. Explicit empty region returns 1 from `_main`, but its caller ignores
that value and exits successfully. Missing organization domain calls nonexistent
`os.exit`. The last case was reproduced; other paths follow from source.

### F26 — P2: Empty backend JSON crashes

`rules/common/terraform.py:74-77,84-93`. Valid JSON `{}` becomes a dict but is
compared with the string `"{}"`, then indexed for missing `bucket`. Reproduced
`KeyError('bucket')`. Validate the decoded object and distinguish absent/empty
backend settings consistently.

### F27 — P1: Failed initialization/workspace selection does not stop execution

`rules/common/terraform.py:84-106`,
`rules/run_terraform/run_terraform.py:110-125`. Init discards the failure result.
Workspace selection tries creation on any failure and discards that result too;
the requested operation still runs, potentially against the previously selected
workspace. Reproduced both discarded results using mocked subprocess behavior.

### F28 — P2: Terraform receives options its subcommand does not support

`rules/common/terraform.py:127-136`. The generic builder injects `-var` into
`version`, and `-input=false` into commands such as `fmt`. These flags
are not valid uniformly across Terraform subcommands. Reproduced the `version`
argument vector using a mocked process; verified against
[Terraform's version reference](https://developer.hashicorp.com/terraform/cli/commands/version).

### F29 — P2: Terraform loses the caller's process environment

`rules/common/terraform.py:140-162`. `envs` starts empty and replaces, rather than
extends, the child environment. PATH, HOME, TF_VAR values and authentication
environment variables disappear; absent optional settings override profile and
kubeconfig with empty strings. Reproduced using only dummy environment values.

### F30 — P2: Terraform changes caller state instead of restoring it

`rules/common/terraform.py:99-100,178-182`,
`rules/run_terraform/run_terraform.py:125-129`. An existing AWS_REGION is deleted
instead of restored (reproduced). Workspace cleanup always switches to default,
not the workspace active before the invocation, and cleanup failures are ignored
(static). Track and restore previous state.

### F31 — P1: Template and kubeseal rule scripts silently do nothing

`rules/file_template/rule.py:5-57`, `rules/kubeseal/kubeseal.py:5-104`.
Both files define functions only; neither parses CLI arguments nor invokes its
function. The runner launches scripts as processes rather than importing/calling
these functions. Reproduced direct execution: exit 0 with no output, even with
an invalid argument.

### F32 — P2: A template output basename fails

`rules/file_template/rule.py:54`. `output="output.txt"` calls
`os.makedirs("")` and raises FileNotFoundError. Reproduced with a harmless
template and empty synthetic environment.

### F33 — P2: Kubeseal uses a nonexistent output flag

`rules/kubeseal/kubeseal.py:84-88`. It passes `--output`, whereas the upstream CLI
defines `--sealed-secret-file`/`-w`. Mocked argument capture confirmed what Kamaji
sends; checked the [upstream flag definitions](https://github.com/bitnami/sealed-secrets/blob/main/cmd/kubeseal/main.go).
No cluster was contacted.

### F34 — P2: Disabled certificate fetching passes None to subprocess

`rules/kubeseal/kubeseal.py:26,31,88`. `fetch_cert=False` without `cert_file`
puts None in argv. Reproduced argument construction with all I/O mocked;
real Popen rejects a None argument. Validate this combination or omit --cert
and use the intended live-cluster mode.

### F35 — P2: Controller ambiguity is swallowed

`rules/kubeseal/kubeseal.py:51-64`. The deliberately raised multiple-controller
ValueError is caught by the surrounding broad exception handler. Processing
continues and may fall back to kube-system despite requiring an explicit choice.
Reproduced using mocked deployment data.

### F36 — P1: Certificate fetching uses one shared predictable file

`rules/kubeseal/kubeseal.py:32,78-80`. All processes/clusters write
`/tmp/kamaji_pub_cert.pem` using a normal truncating open. Concurrent calls can
seal with another cluster's certificate; a pre-existing symlink can redirect the
write. Static; the real path was never opened. Use a private per-invocation file.

### F37 — P2: 1Password initialization raises NameError

`rules/common/one_password.py:36`. `setAccount` references undefined
`ORG_DOMAIN` instead of `self.org_domain`. Reproduced on an uninitialized test
instance, without invoking 1Password.

### F38 — P2: 1Password pipelines mishandle data and empty results

`rules/common/one_password.py:36-39,50-63,68-82`. Arguments are interpolated into
shell pipelines without safe quoting, so metacharacters can become commands.
`pipefail` makes a grep no-match raise CalledProcessError before the intended
empty-result fallback. JSON is decoded with stripping and repeated
`unicode_escape` transformations rather than a JSON parser, which can corrupt
backslashes/Unicode in returned values. Static; no secret retrieval was run.

### F39 — P2: Tests do not provide the coverage their names imply

`runner/runner_test.go:11-72` never invokes Run or prepareCmdline.
`rt/rt_test.go:37-43` sets WorkspaceDir to its fixture but InitRuntime overwrites
that by searching actual cwd; no chdir is performed. It exits the test process
when no marker exists in cwd or its ancestors. On this machine it passed by
finding `/Users/odemir/Development/kamaji.workspace.yaml`, whose existence was
checked afterward without reading its contents; neither the repository nor
`rt/` contains that marker. Thus it tests an external workspace instead of its
fixture. `TestSetupPythonEnv` depends on
system Python and global requirements and may perform real pip/network work.
Runner no-op coverage was confirmed by source plus passing baseline tests.

### F40 — P3: Generated local artifacts are tracked

`git ls-files` includes
`rules/run_terraform/__pycache__/run_terraform.cpython-313.pyc` and
`test/.terraform/environment`, despite ignore patterns for those artifact
families. The tracked Terraform workspace marker can carry a stale workspace
selection into another checkout. Contents were not read or changed.

### F41 — P2: Global rules installation destroys the old tree before copy succeeds

`utils/utils.go:24-60`. After a shallow existence check, the installer removes
the entire destination before walking/copying the source. A later read/write
failure leaves the installation missing or partial, with no rollback. Running
from the installed rules parent can delete the source itself. Static only;
no global installation/deletion command was run.

### F42 — P3: Staticcheck reports existing maintenance defects

`target/target_test.go:4` imports deprecated `io/ioutil` (SA1019).
`tools/tools.go:80` assigns `binaryFilePath` without using the new value
(SA4006). Both existed before the upgrade and remain; the assignment's line
number shifted because of the import cleanup. The final staticcheck command
returned exit 1, so the standing stop-on-red rule prevented further code edits.

## Verification and limitations

The focused baseline command `go test ./target ./runner -count=1 -v` passed
TestParseBuildFile, TestRun and TestPrepareCmdline before upgrades. The latter
two tests only exercise their own fixture setup, as explained in F39.

`.audit/probes/probe_test.go` holds repository-confined demonstrations, not
correctness gates: a PASS means the named defect was reproduced. Synthetic
archive traversal stays within the audit directory. The Python probes used
mocked subprocesses and synthetic environment values; all six rules parse.

Original test files remain unchanged: rt/rt_test.go, runner/runner_test.go,
target/target_test.go. Static assertion/guard call counts before and after are
11/11, 7/7 and 6/6 respectively, total 24/24. Predicate: AST call expressions
starting `t.Fatal(`, `t.Fatalf(`, `t.Error(` or `t.Errorf(`, including setup guards;
this is not a count of distinct behavioral properties.
